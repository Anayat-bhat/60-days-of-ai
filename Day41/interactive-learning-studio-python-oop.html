MODULE 1

Classes & Objects — The Foundations

Difficulty: Foundational
Core Concept

A class is a blueprint. An object (or instance) is a concrete thing built from that blueprint. Python builds every object through a special method: __init__, which runs automatically when you create a new instance and sets up its starting state (its attributes).

class Student:
    def __init__(self, name, gpa):
        self.name = name       # instance attribute
        self.gpa = gpa

    def study(self, hours):
        boost = hours * 0.02
        self.gpa = min(4.0, self.gpa + boost)
        return f"{self.name} studied {hours}h, GPA now {self.gpa:.2f}"

# Creating objects from the blueprint
alex = Student("Alex", 3.2)
priya = Student("Priya", 3.8)
print(alex.study(5)))  # Alex studied 5h, GPA now 3.30

self is simply "this particular object" — it's how a method refers to the instance it was called on. Every method you define on a class receives self as its first parameter automatically.

Analogy

A class is like a cookie cutter; objects are the cookies. The cutter (class Student) defines the shape — every cookie will have a name and a gpa slot — but each cookie (alex, priya) is baked separately and can have different values filled in.

One class → many independent objects, each with its own attribute values

Comparison: Function-based vs. Class-based state

ApproachExampleTrade-off
Plain dict/functionstudent = {"name": "Alex", "gpa": 3.2}Simple, but no bundled behavior or validation
Class + objectStudent("Alex", 3.2)Bundles data + behavior, supports inheritance & invariants
Common Misconception

"self is a Python keyword." It isn't — it's just a convention (any name would technically work). Python passes the instance as the first argument automatically; calling it self is a near-universal community standard you should always follow.

Practical Exercise

Write a Car class with attributes make, model, and fuel (starts at 100). Add a method drive(miles) that reduces fuel by miles * 0.1.

Hint: set self.fuel = 100 inside __init__, then subtract in drive.
class Car:
    def __init__(self, make, model):
        self.make = make
        self.model = model
        self.fuel = 100

    def drive(self, miles):
        self.fuel -= miles * 0.1
        self.fuel = max(0, self.fuel)
Key Takeaways
  • A class defines structure (attributes) and behavior (methods); objects are instances of it
  • __init__ runs automatically on creation to set initial state
  • self refers to the specific object a method is operating on
  • Each object keeps its own independent copy of instance attributes

MODULE 2

Encapsulation & Methods

Difficulty: Building
Core Concept

Encapsulation means bundling data with the code that protects it, so objects control their own state instead of letting outside code corrupt it. Python doesn't have true "private" attributes, but it has strong conventions and tools: a single underscore (_balance) signals "internal, don't touch," and the @property decorator lets you add validation while keeping clean attribute-style access.

class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self._balance = balance   # internal convention

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, amount):
        if amount < 0:
            raise ValueError("Balance can't go negative")
        self._balance = amount

acct = BankAccount("Priya", 500)
acct.balance = 600       # calls the setter, validated
print(acct.balance)  # calls the getter → 600

Instance vs. Class vs. Static Methods

class Circle:
    pi = 3.14159   # class attribute

    def __init__(self, r):
        self.r = r

    def area(self):        # instance method
        return Circle.pi * self.r**2

    @classmethod
    def unit_circle(cls):   # alt constructor
        return cls(1)

    @staticmethod
    def is_valid_radius(r):  # utility
        return r > 0

Instance methods (self) act on one object's data.

Class methods (cls) act on the class itself — often used as alternate constructors.

Static methods take neither — they're just organized inside the class namespace for relevance.

Analogy

Encapsulation is like a vending machine: you interact through the coin slot and buttons (the public interface — balance, deposit()), never by reaching inside to rewire the coin mechanism directly (_balance). The machine decides what's a valid operation.

Try it: Getter/Setter Behavior
acct.balance = 500  → OK, balance is now 500
Common Misconception

"Underscore attributes are truly private, like in Java." A single underscore is only a convention — Python still lets you access obj._balance directly. Double-underscore (__balance) triggers "name mangling," making accidental access harder, but nothing in Python is unbreakably private. Encapsulation here is a social contract enforced by good API design, not the compiler.

Practical Exercise

Add a @property called temperature to a Thermostat class that raises a ValueError if set below -50 or above 50.

Hint: use @property for the getter and @temperature.setter for the validated setter.
class Thermostat:
    def __init__(self):
        self._temperature = 20

    @property
    def temperature(self):
        return self._temperature

    @temperature.setter
    def temperature(self, value):
        if not -50 <= value <= 50:
            raise ValueError("Out of range")
        self._temperature = value
Key Takeaways
  • Encapsulation protects state by controlling access through methods/properties
  • _single_underscore = convention; __double_underscore = name-mangled
  • @property/@setter give validated, attribute-style access
  • Instance / class / static methods differ in what they receive and operate on

MODULE 3

Inheritance & Polymorphism

Difficulty: Applying
Core Concept

Inheritance lets a class (child/subclass) reuse and extend another class (parent/superclass). Polymorphism means different classes can respond to the same method call in their own way — the caller doesn't need to know exactly which class it's dealing with.

class Animal:
    def __init__(self, name):
        self.name = name
    def speak(self):
        return f"{self.name} makes a sound"

class Dog(Animal):          # Dog inherits from Animal
    def speak(self):        # method override
        return f"{self.name} says Woof!"

class Cat(Animal):
    def speak(self):
        return f"{self.name} says Meow!"

for pet in [Dog("Rex"), Cat("Milo")]:
    print(pet.speak())  # polymorphism: same call, different behavior

Use super().__init__(...) inside a child's __init__ to run the parent's setup logic before adding the child's own attributes — avoiding duplicated code.

Inheritance tree with method overriding (polymorphism)
ConceptWhat it doesExample
InheritanceReuse parent structure/behaviorclass Dog(Animal):
OverrideReplace a parent method in a childredefining speak() in Dog
super()Call the parent's version of a methodsuper().__init__(name)
Duck typing"If it walks like a duck..." — no shared base class needed, just matching methodsany object with .speak() works in the loop above
Analogy

Think of Animal as a job description template ("must be able to speak()"), and Dog/Cat as specific employees who each perform that duty their own way. HR (your code) only cares that everyone can do speak() — not how each one does it.

Common Misconception

"Inheritance is always the right way to share code." Deep inheritance chains get fragile and hard to reason about. If the relationship isn't truly "is-a" (a Dog IS AN Animal), prefer composition ("has-a") instead — covered in Module 4.

Practical Exercise

Create a Shape base class with a method area() returning 0, then Rectangle and Triangle subclasses that override area() correctly.

Hint: Rectangle.__init__ takes w, h; Triangle.__init__ takes base, height.
class Shape:
    def area(self):
        return 0

class Rectangle(Shape):
    def __init__(self, w, h):
        self.w, self.h = w, h
    def area(self):
        return self.w * self.h

class Triangle(Shape):
    def __init__(self, base, height):
        self.base, self.height = base, height
    def area(self):
        return 0.5 * self.base * self.height
Key Takeaways
  • Inheritance models "is-a" relationships and enables code reuse
  • Overriding lets subclasses customize inherited behavior
  • super() calls the parent's implementation without duplicating code
  • Polymorphism + duck typing let you write code that works across many types

MODULE 4

Mastery: Dunders, Composition & Patterns

Difficulty: Mastery
Core Concept: Dunder (Magic) Methods

Dunder methods (double-underscore, like __init__) let your objects integrate with Python's built-in syntax: printing, comparison, arithmetic, length, iteration.

class Vector:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __repr__(self):
        return f"Vector({self.x}, {self.y})"

    def __add__(self, other):
        return Vector(self.x + other.x, self.y + other.y)

    def __eq__(self, other):
        return (self.x, self.y) == (other.x, other.y)

v1, v2 = Vector(1,2), Vector(3,4)
print(v1 + v2)      # Vector(4, 6) — via __add__
print(v1 == Vector(1,2))  # True — via __eq__

Composition: "Has-a" instead of "Is-a"

class Engine:
    def start(self):
        return "Engine roaring"

class Car:
    def __init__(self):
        self.engine = Engine()  # Car HAS an Engine

    def start(self):
        return self.engine.start()

A Car is not an Engine — it has one. Composition builds objects out of other objects, avoiding rigid inheritance chains. Prefer composition when the relationship is "part of" rather than "a kind of."

Composition: diamond = "has-a" ownership relationship

A Glimpse of Design Patterns

PatternIdeaPython-flavored example
FactoryA method that creates and returns objects@classmethod def from_json(cls, data): ...
SingletonOnly one instance ever existsmodule-level instance, or override __new__
ObserverObjects subscribe to be notified of changesa list of callback functions called on state change
Analogy

Dunder methods are like giving your object a universal remote control — Python's built-in operators (+, ==, len(), print()) become buttons that work on your custom object because you defined what each button does.

Common Misconception

"Composition and inheritance are mutually exclusive." Real systems mix both. A common guideline: "favor composition over inheritance" for flexibility, but inheritance is still the right tool for genuine is-a hierarchies (like the Shape example in Module 3).

Practical Exercise

Add __len__ and __str__ to a Playlist class that wraps a list of song titles, so len(playlist) and print(playlist) work naturally.

Hint: __len__ must return an int; __str__ must return a string.
class Playlist:
    def __init__(self, songs):
        self.songs = songs

    def __len__(self):
        return len(self.songs)

    def __str__(self):
        return f"Playlist({len(self)} songs)"
Key Takeaways
  • Dunder methods integrate custom objects with Python's built-in syntax
  • Composition ("has-a") is often more flexible than deep inheritance ("is-a")
  • Design patterns are reusable, named solutions to recurring OOP problems
  • Mastery = choosing the right tool (class, inheritance, composition) per situation

Final Challenge

Build a Library System

Combine everything: classes, encapsulation, inheritance, and dunder methods.

Task: Design a Book class (title, author, _is_checked_out) and a Library class that holds a list of Book objects with methods checkout(title) and return_book(title). Add an EBook subclass of Book with an extra file_size_mb attribute, and give Library a __len__ returning the number of books.

Hint: EBook(Book) should call super().__init__(title, author) then set self.file_size_mb.
class Book:
    def __init__(self, title, author):
        self.title, self.author = title, author
        self._is_checked_out = False

class EBook(Book):
    def __init__(self, title, author, file_size_mb):
        super().__init__(title, author)
        self.file_size_mb = file_size_mb

class Library:
    def __init__(self):
        self.books = []

    def checkout(self, title):
        for b in self.books:
            if b.title == title and not b._is_checked_out:
                b._is_checked_out = True
                return True
        return False

    def __len__(self):
        return len(self.books)

Summary Notes

  • Classes bundle data + behavior; objects are independent instances of a class
  • Encapsulation protects internal state via conventions and properties
  • Inheritance shares structure/behavior for true "is-a" relationships; use super() to extend, not replace, parent logic
  • Polymorphism/duck typing let different objects respond to the same call in their own way
  • Dunder methods integrate custom objects into Python's built-in syntax
  • Composition ("has-a") is often more flexible than deep inheritance chains
